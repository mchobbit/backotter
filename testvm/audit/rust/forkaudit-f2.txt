test with --exact --test-threads 1, TMPDIR in RAM (tmpfs), a TMPDIR of its
own for every run.

1. The asked-for 200 runs, 4 at a time:
     fork f0d01fd:               13 of 200 fail (6.5%)
     stock rustic_core-v0.14.0:   0 of 200 fail

2. The full error, the same in every failing run (the tree id varies):
     [crates/core/tests/integration/prune.rs:239:5] repo.check(check_opts) = Ok(
         CheckResults([(Error, ErrorCheckingTrees { source: RusticError {
             kind: Internal,
             guidance: "Tree ID `{tree_id}` not found in index",
             docs_url: None, error_code: None, ask_report: false,

             backtrace: Some(<disabled>) } })]))
     Error: `rustic_core` experienced an error related to `the repository`.
     Message: check found errors!
   The test's last line fails: dbg!(repo.check(check_opts))?.is_ok()?.
   No panic, no hang, no sanitizer report (ASan and TSan ran this test too).

3. It is not a race inside one run.  It depends on what other processes do
   to the directories above the test's source while it runs:
     one run at a time, nothing else running      fork 0 of 200, stock 0 of 200
     one at a time, 24 busy loops beside it       fork 0 of 200
     4 at a time, every run's TMPDIR made before
       the first run and removed after the last   fork 0 of 400
     4 at a time, TMPDIRs made and removed as
       the runs come and go (as in 1)             fork 33 of 400, 55 of 400
     12 at a time, the same                       fork 21 of 400, stock 0 of 400
     one at a time, a loop making and removing a
       directory beside TMPDIR every 20 ms        fork 3 of 400, stock 0 of 400
     one at a time, the same loop without pause   fork 0 of 200, stock 0 of 200
     one at a time, that loop inside TMPDIR       fork 0 of 200, stock 0 of 200

4. What decides it: whether the snapshot's tree changes between the test's
   three backups of the same path.  400 fork runs, 4 at a time, printing the
   three snapshots' tree ids:
     tree1 = tree2 = tree3      161 runs    0 fail
     tree1 = tree2, tree3 new    67 runs    0 fail
     tree2 new, tree3 new       113 runs    0 fail
     tree2 new, tree3 = tree2    59 runs   31 fail
   So the source's tree changed under the test in 239 of 400 runs, though
   the test changes nothing: the fork stores the directories above a
   backed-up path with their own metadata (66d95b2, archiver/tree.rs
   with_dir_nodes, as restic does), and one of them is the directory the
   runs' TMPDIRs are made and removed in, whose mtime and ctime move.
   (The backed-up path is one file, <TMPDIR>/<tempdir>/0/0/9/2.)
   Stock gives those directories nodes of its own making (mode 755, no
   times), so its tree never changes.  In fork-tests.sh the same directory
   is the shared TMPDIR of all the integration tests.

5. The same on purpose, one run at a time (the test copied as a variant
   that changes one thing between the first and the second backup and
   nothing between the second and the third; scratch only, 60 runs each):
     nothing changed                             fork 0 of 60    stock 0 of 60
     the directory above the path gets a new
       mtime (a directory made and removed in it) fork 36 of 60  stock 0 of 60
     the backed-up file itself gets a new mode   fork 31 of 60   stock 36 of 60
   (An earlier pass of the same variants: fork 47 and 40 of 60, stock 34 of
   60 for the file.)  In every failing run the tree "not found in index" is
   the third snapshot's, which is also the second's; the stale second plan
   failed in every run, passing or failing.  Changing the same thing before
   the third backup as well makes all 60 pass.
   So stock 0.14.0 has the defect too: it fails in about half the runs once
   the source really changes between the first and second backup.  The fork
   only reaches it more easily, because more of what it stores can change.
   Why about half the runs of that case fail and half pass was not found
   out.

6. For unit G8.  The test runs prune with keep_marked 0 (PruneOptions::
   default().keep_marked(Span::default()); the default is 23 hours) and
   executes a stale plan on purpose, then expects check to pass after
   repair_index.  What fails is upstream code (prune, the indexer, repair
   index); none of our hunks is in prune.rs or check.rs.  Ours is the
   trigger: 66d95b2 makes a snapshot's tree depend on the times of every
   directory above the backed-up path.
